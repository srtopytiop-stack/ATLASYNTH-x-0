# خارطة طريق التطوير

## الحالة الحالية: نواة v0.1.0

الذي أُنشئ في هذه الحزمة: API أساسي، بيانات Spot عامة، خصائص، مصنف نظام بسيط، نماذج GARCH/HMM مرجعية، ثلاث استراتيجيات baseline، باكتيست، مقاييس، تحقق إحصائي، تقدير مخاطر نظري، تقرير بحث، إشعار Telegram اختياري، واجهة RTL مبدئية واختبارات Python.

هذا لا يعني أن المشروع إنتاجي أو أن الاستراتيجيات مربحة. واجهة الويب لم تُبنَ بنجاح في بيئة الإنشاء لأن تنزيل npm dependencies انتهى بمهلة؛ بناء CI في بيئة متصلة يجب أن يثبت ذلك.

## المرحلة 0 — خط أساس قابل لإعادة البناء

- تشغيل الاختبارات على Python 3.12 في GitHub Actions.
- تثبيت dependencies الواجهة والتحقق من `npm run build`.
- توثيق متغيرات البيئة ونقاط API.
- ربط نسخة الحزمة بـ commit واضح في مستودع جديد.
- عدم تشغيل أي مفاتيح حساب أو أي تداول حي.

**قبول:** `pytest`, `compileall`, `npm run build` ناجحة، وإعداد الأمان يعرض القيم المعطلة فعليًا.

## المرحلة 1 — عقد البيانات والتخزين

- تصميم schema للإصدارات، التجارب، المعلمات، بصمة البيانات، النتائج والسجلات.
- إضافة تخزين SQLite محلي اختياري أو Postgres من خلال repository interface.
- حفظ run IDs قابلة لإعادة الإنتاج وحالات فشل التجارب.
- سياسة احتفاظ/تصدير للنتائج.

**قبول:** تصدير وإعادة تحميل تجربة دون تغيير صامت بالمدخلات؛ migrations واختبارات تكامل للتخزين.

## المرحلة 2 — عميل البيانات المتين

- اختبار كل endpoint العام، حدود الطلب، retries backoff مع jitter، circuit breaker، cache TTL ومراقبة الفشل.
- دعم أكثر من quote asset كإعداد مستقبلي دون تمرير رموز leveraged أو أزواج غير مؤهلة.
- توحيد مفهوم freshness وdata quality.
- إضافة اختبارات عقود بمخازن HTTP مسجلة، لا الاعتماد على شبكة حية في CI.

**قبول:** أخطاء البيانات وانقطاع الخدمة لا ينتجان نتائج سوق مختلقة؛ الالتزام بحدود الاستدعاء.

## المرحلة 3 — المحركات الكمية

- إضافة اختبارات مرجعية مستقلة للـ RSI/ATR/ADX والخصائص.
- تقييم نماذج السوق على walk-forward منفصل.
- إضافة fit/diagnostics حقيقيين لـ GARCH أو عدم عرضه كنموذج مقدّر.
- ضبط اختيار عدد حالات HMM واختبار label switching وlikelihood/convergence.
- إضافة سجل إعدادات استراتيجية قبل الاختبار.

**قبول:** تقرير يحتوي تعريف النموذج والنافذة والتقارب والقيود؛ نتائج خارج العينة.

## المرحلة 4 — بحث الاستراتيجيات والتحقق

- مصفوفة عوائد متزامنة لعدة استراتيجيات.
- CSCV/PBO مدقق مقابل fixture منشور أو مرجع مستقل.
- DSR يتحقق من عدد المحاولات وافتراضات توزيع القيم، مع تحذيرات عدم كفاية البيانات.
- embargo/purge حيث يوجد تداخل labels أو أفق الاحتفاظ.
- اختبار ضد تسرب المستقبل باستخدام بيانات مستقبلية معدلة وبادئات مختلفة.
- فصل dataset تطوير عن dataset نهائي محفوظ.

**قبول:** لا يرفع أي نتيجة مختبرة على بيانات الاختيار نفسها إلى حالة «متحقق خارج العينة».

## المرحلة 5 — وكيل البحث

- أدوار مستقلة: Data Quality, Regime, Strategy Research, Validation, Risk, Skeptic/Counterexample, Report.
- كل دور يدخل بعقد مكتوب ويخرج أدلة قابلة للفحص.
- يمنع الوكيل تغيير استراتيجية أو عتبة ثم تسمية الاختبار نفسه مستقلًا.
- سجل فرضيات فاشلة وأسباب الرفض.
- بحث آلي محدود بعدد التجارب والوقت؛ لا infinite loop.
- LLM اختياري لصياغة الأسئلة/التقارير فقط ما لم توجد وسيلة للتحقق من مخرجاته.

**قبول:** كل تغيير ينتج run id جديدًا؛ لا حذف للنتائج السلبية؛ التقييم النهائي محجوز.

## المرحلة 6 — أداء وتجربة استخدام

- تحسين المسح متعدد الأصول عبر queue/rate limiter وcache، دون إغراق API.
- إضافة اختيار الأطر الزمنية وإظهار timestamps والبيانات القديمة.
- رسوم equity/drawdown/returns والتوزيع والتكاليف بوضوح.
- إمكانية تصدير CSV/JSON وتقرير قابل للأرشفة.
- تحسين الهاتف وإتاحة تقليل الحركة.

**قبول:** الواجهة لا تظهر بيانات mock في بيئة الإنتاج ولا تتجمد خلال الطلبات.

## المرحلة 7 — نشر مضبوط

- نشر الواجهة والخدمة الخلفية بخطط منخفضة التكلفة وتوضيح القيود.
- CORS صارم، HTTPS، rate limits، health/readiness، logs لا تحتوي أسرارًا.
- secrets عبر host secret manager.
- healthchecks ونسخة احتياطية للتخزين.

**قبول:** build/CI نظيفان، مراقبة فشل البيانات، لا credentials خاصة بالبورصة، لا endpoint تنفيذ.

## مؤشرات نضج لا وعود ربح

- معدل تغطية الاختبارات للمسارات الخطرة.
- عدد أخطاء البيانات التي تم كشفها مقابل المخفية.
- نسبة التجارب القابلة لإعادة الإنتاج.
- نتائج الفجوة بين in-sample وout-of-sample.
- أداء بعد تكلفة افتراضية وحساسية الرسوم والانزلاق.
- استقرار النتائج عبر أنظمة سوق مختلفة.
- معدلات فشل الخدمة ووقت استجابة المسح.

لا نستخدم هدف «تحقيق نسبة فوز X%» كمعيار هندسي، لأن نسبة الفوز وحدها لا تصف التوقع أو المخاطر.
